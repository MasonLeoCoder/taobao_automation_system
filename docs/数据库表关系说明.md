## 1. 以后建表和改表的固定交付要求

每次数据库结构变更必须同时交付：

1. **数据库表备注**：写入中文名称和业务用途，如 `tasks` 的备注为“任务记录表：保存任务状态、起止时间、结果及执行归属”。
2. **数据库字段备注**：每个字段写清中文名称和含义。状态说明口径，数量和价格说明单位，时间说明时区，外键注明目标，空值说明未知或未关联的含义。
3. **完整字段字典**：包括英文表名/字段名、中文名称、类型与长度/精度、是否可空、默认值、业务含义、单位/时区、状态取值及主键/唯一键/外键。JSON 字段还要说明内部业务结构、版本和未知值规则。
4. **每张表的关联说明**：上游和下游表、对应字段、关联基数、可空性、物理外键或逻辑关联、更新和删除规则，以及必要的归属校验；独立表明确注明。
5. **实际结构核对结果**：对照数据库中的备注、字段和约束复查文档，不能出现文档有备注但数据库没有备注的情况。
6. **字段取值说明**：统一维护[数据库字段取值说明](数据库字段取值说明.md)，覆盖所有字段的取值/填写规则，说明状态代码、中文含义、产生条件、空值、单位、时区及JSON内部结构；区分约束、实际生成、兼容、测试与预留。业务取值改变但没有DDL时同样维护。

表名和字段名继续使用现有英文命名规范，中文名称通过备注与字典表达。备注须写入MySQL原生`COMMENT`；代码注释只作补充。SQLAlchemy模型与有序迁移同步保存备注。[完整逐字段字典](数据库字段字典.md)覆盖当前245个字段，后续表结构变更同步维护。

备注示例：

| 对象 | 中文名称 | 备注应表达的内容 |
|---|---|---|
| `tasks.id` | 任务编号 | 32 位任务标识，保留历史编号，主键 |
| `task_events.task_id` | 所属任务编号 | 关联 `tasks.id`；空值表示无法可靠确定任务归属 |
| `sku_observations.price_value` | 已解析价格 | 定点数，币种见同记录 `currency`；空值表示未取得可靠数值，不等同于 0 |
| `task_events.occurred_at` | 事件发生时间 | 北京时间（UTC+08:00）；历史时间无可靠时区时为空，原文见 `time_raw` |
| `product_current_sections.scope_key` | 采集范围键 | 按带版本的规范化采集条件生成，区分限定样本、筛选和排序范围 |

## 2. 全部 18 张业务表的名称与关联

下表给出每张表的建议中文名称（用于表备注的开头）、用途、上游和下游。箭头表示业务引用方向，具体列见后续各节。当前不包含历史导入管理表。

| 英文表名 | 中文名称 | 业务用途 | 上游引用 | 下游引用 |
|---|---|---|---|---|
| `tasks` | 任务记录表 | 任务状态、结果、执行资源和进程归属 | 无业务必需父表，由统一任务执行器创建 | 事件、整次商品采集、模块批次、页面记录、媒体引用 |
| `task_events` | 任务事件日志表 | 进度、日志、异常、人工提示及任务内顺序 | 可选任务、整次采集、模块批次 | 无直接业务子表，作为历史查询与未来实时显示的数据源 |
| `products` | 商品身份表 | 平台与商品编号的统一身份 | 可选标题来源批次 | 整次采集、模块批次、页面记录、列表观察、当前结果指针 |
| `collection_runs` | 商品采集运行表 | 某商品本次所选模块的整体汇总 | 商品、可选任务、详情入口 | 模块步骤、模块批次、事件 |
| `collection_steps` | 采集模块步骤表 | 未启用、未执行、运行和结束等步骤状态 | 整次商品采集 | 该步骤的一个或多个模块批次 |
| `collection_batches` | 采集模块批次表 | 模块实际结果、搜索来源、采集范围和覆盖状态 | 可选任务、商品、运行、步骤、来源批次、搜索输入图片文件 | 各类采集明细、媒体、检查点、当前结果指针、事件、派生批次、标题来源引用 |
| `product_current_sections` | 商品当前有效结果表 | 各模块和范围的最新有效批次指针 | 商品、模块批次 | 无直接子表；查询时解析到批次结果 |
| `search_records` | 页面搜索与入口记录表 | 搜索方式、搜索词或详情入口的观察记录 | 可选任务、商品、来源列表观察、搜索输入图片文件 | 商品详情运行；截图通过同任务媒体引用与page_logical_key追溯 |
| `list_observations` | 列表商品观察表 | 商品在某批列表中的位置与展示字段 | 列表批次、可选商品 | 来源详情入口；媒体链接保留在该观察记录中 |
| `sku_observations` | 商品规格观察表 | 本批 SKU 组合、价格和确认状态 | SKU 批次 | SKU 媒体引用 |
| `parameter_observations` | 商品参数观察表 | 本批参数名称、值和顺序 | 参数批次 | 无直接子表 |
| `review_summaries` | 评价概览表 | 本批评价数量、好评率和总结标签 | 评价概览批次 | 无直接子表；标签先存 JSON |
| `review_observations` | 用户评价观察表 | 本批评价正文、身份依据、规格和追评 | 评价明细批次 | 评价媒体引用 |
| `question_observations` | 商品问题观察表 | 本批问题及回答采集完整性 | 问答批次 | 回答明细、问题媒体引用 |
| `answer_observations` | 商品回答观察表 | 问题下的回答、身份、标签与规格 | 问题明细 | 回答媒体引用 |
| `file_assets` | 本地文件索引表 | 本地文件路径、校验值与可用状态 | 无业务必需父表，通过媒体引用关联采集来源 | 一个文件可被多个媒体、证据、搜索记录或采集批次引用 |
| `media_references` | 媒体与证据引用表 | 源链接、用途、顺序与本地文件的关联 | 可选任务、批次、具体明细、本地文件 | 无直接子表 |
| `collection_checkpoints` | 采集检查点表 | 去重键、逐项处理状态、阶段及复用信息 | 模块批次 | 无直接子表；恢复仍由业务独立核对 |

业务表总数为18。另有技术表`alembic_version`，中文备注为“数据库迁移版本表：记录已完成的结构升级版本，无业务外键”，主键`version_num`带中文说明；当前版本为`0006_list_sales`。该表不计入18张业务表。

```mermaid

    P[商品 products] -->|一个商品多次运行| R
    R -->|一次运行多个步骤| S[步骤 collection_steps]
```

媒体引用的四种具体明细外键最多填写一种；至少具备任务、批次或一种具体明细归属。多层上下文同时填写时，任务、商品和批次必须一致。约束由数据库外键/检查约束及必要的事务归属校验共同保证，正式迁移文档注明各项的实现方式。

本地文件逻辑上按 `(root_key,relative_path)` 唯一；实际索引为 `(root_key,path_key)`，`path_key` 是按文件系统规则规范化的相对路径 SHA-256，避免长路径超过索引长度。完整路径仍保留，写入服务须核对路径哈希与原路径不冲突，不能将内容哈希当成业务身份。历史批次指向独立历史文件，最新副本单独登记；不因内容相同就删除另一用途或另一历史批次的文件。原始JSON等文件通过媒体引用、任务/批次归属和文件哈希追溯。

## 5. 历史导入能力退役（0005）

import_runs、import_sources、import_row_mappings、import_issues已移除；tasks、task_events、search_records、collection_runs、collection_batches的import_run_id及其外键同步移除。没有替代的导入表或隐含导入关联。

实时数据继续按任务、商品、入口、运行、批次和明细外键追溯。批次visibility和当前有效分区完整性规则保留；正常历史查询不再依赖导入状态。本地持久流水仅补写已经执行的实时操作，属于保留能力。

旧关系及取值仅适用于0001～0004，见[退役功能说明](历史记录/历史导入功能说明（0001至0004）.md)；本次迁移范围与数据核对见[精简记录](变更记录/历史导入能力精简记录.md)。

## 6. 全局更新、删除和关系校验规则

- 主键默认不可修改；计划中的业务外键默认限制删除与更新。父记录仍被历史明细、当前指针、事件或来源引用时，不级联删除历史资料。未来若需要例外，必须在对应迁移与本关系文档中明确列出。
- 允许为空的外键必须说明原因；原平台编号或来源批次缺失不以 `0`、空字符串或虚构父记录替代。
- 任务、运行、步骤、批次、商品的多层归属需核对一致。可由复合唯一键/复合外键表达的关系优先落实为数据库约束，不能只验证单个 ID 存在。
- 自引用派生来源必须避免循环；数据库外键与程序维护的逻辑关系明确区分。
- 没有直接业务子表的字典、记录或技术表也必须出现在完整表清单中；“无直接子表”不等于可以省略用途、来源及生命周期说明。
- 备注、字段含义或关联含义有变化时，通过新增有序迁移同步数据库和文档；不修改已经应用的旧迁移假装历史结构已变。


箭头表示业务流向；具体外键是子表字段指向父表主键/唯一键，实例如批次75→旧SKU66、观察9→批次75，见拆分实施记录。


### Web剩余模块补采的来源关系

无DDL或外键变化。补采所有模式复用一个新tasks及一个商品collection_runs，所选模块各有自己的collection_batches。已有有效模块按全局product_current_sections判断跳过，仍属于原任务/运行，不复制旧批次、不改写原搜索观察或旧资料归属。remaining为collection_jobs.payload中的申请模式标记，不进入数据库module列。新任务已保存模块确认入库后显示各自batch链接；再次补采按全局有效资料重新计算范围，不能将进度描述当作浏览器断点恢复。


### SKU 禁用规则归类的派生关系（2026-10-25）

不新增表或字段。规则归类创建同商品、同skus模块的新collection_batches，derivation_kind=sku_stock_rule；upstream_batch_key来源于record.stock_rule_source_batch_key，derived_from_batch_id通过已有程序校验解析为原批次外键，禁止跨商品、自引用和成环。新sku_observations、collection_checkpoints及media_references归属新批次；图片继续保留原来源并核对文件校验值。通过完整性检查后，product_current_sections.sku_details指向新批次。新task_id为规则归类任务，原采集批次和观察业务内容不改，captured_at保留原观察时间；原批次导出/最后尝试选择控制键可随发布调整。

## 采集恢复与补采（0008）

0008时模型schema_v8，共23张业务表及1张迁移表；当前已升级0009，旧队列表升级为统一申请表，见文末。0001～0008及冻结模型保持不变。全部新增字段取值见[统一说明](数据库字段取值说明.md#采集恢复与补采0008)。

| 表 | 主键/唯一约束 | 上游及外键 | 下游及逻辑关联 |
|---|---|---|---|
| collection_plans | id主键 | id→tasks.id首次执行；active_task_id→tasks.id最近执行，均非空 | executions.plan_id；checkpoint内商品、批次和文件为程序校验的逻辑关联 |
| collection_plan_executions | task_id主键，每执行一条 | task_id→tasks.id；plan_id→collection_plans.id；parent_task_id→tasks.id可空，首次为空 | 原计划一对多执行，每执行一对一任务；恢复只能领取最近执行 |
| collection_discarded_batches | source_batch_key主键 | source_task_id、cleanup_task_id→tasks.id非空；平台商品编号、模块、旧批次为程序核对的逻辑归属 | 对应原collection_batches身份行保留，明细删除，manifest是文件清理凭据；旧快照按标记拒绝重建正文 |
| collection_retry_queue | id主键；execution_key/request_key联合唯一，request_key终态NULL | 排队时尚无任务，无物理外键；payload中的来源由程序校验 | id在启动时成为tasks.id，资源锁和比较原状态领取；没有分布式队列 |

所有新增物理外键均为ON UPDATE RESTRICT、ON DELETE RESTRICT；不级联删除任务或计划。清理只删除目标未完成批次的观察明细和专属文件索引，批次身份、任务、步骤、清理凭据和日志继续保留。共享file_assets由所有引用方核对后保留；已完整批次和product_current_sections指针禁止清理。

同一计划恢复后的详情入口可以引用原执行列表观察：只有两个执行归属同一collection_plans、原列表已保存且商品/关键词/页码等一致才允许。search_records.source_list_observation_id仍是物理外键，计划一致性是额外程序约束，不凭标题猜测来源。

```mermaid
erDiagram

  tasks ||--o| collection_plan_executions : "本次执行"
  collection_plans ||--o{ collection_plan_executions : "恢复执行链"
  tasks ||--o{ collection_discarded_batches : "原任务与清理任务"
```

补采成功时，新的结果和检查点提交后，通过检查点事务给原计划失败项附加resolved_by_task_id；历史错误state保留，当前待处理数量解除。该关联是JSON内的程序维护关系。


## 统一采集申请关系（0009）

当前schema_v9为25张业务表及1张版本表，共315字段。旧collection_retry_queue在核对迁移后移除；collection_plans、collection_plan_executions和collection_discarded_batches继续保留。旧本地派发关系描述属于0009以前的设计，正常入口现统一查询数据库。

| 表 | 上游、主键及唯一关系 | 下游、可空及更新删除规则 |
|---|---|---|
| collection_jobs | id主键；execution_key/submission_key及execution_key/request_key各联合唯一，后两键允许NULL；参数及浏览器资源来自经校验申请 | task_id可空且唯一，物理FK fk_collection_job_task→tasks.id，一次申请零或一次执行、一个执行最多对应一个申请；任务创建同事务建立关联；更新/删除RESTRICT。下游controls.job_id一对多。旧来源task_id只按相同编号核实，不制造任务 |
| collection_queue_states | execution_key独立主键，无物理外键；与jobs.execution_key为一对多逻辑关系，空队列也保留暂停 | 无其他表以外键引用；资源行锁用于提交、领取、暂停串行处理。禁止把共享资源键解释成同一采集任务 |
| collection_job_controls | id主键；job_id不可空，物理FK fk_collection_control_job→collection_jobs.id；更新/删除RESTRICT | 一次申请多条指令；claim_token、prompt_id与当前执行/提示是程序校验逻辑关系，无对应物理外键；无其他表外键引用，保留接收或拒绝记录 |

collection_jobs.payload.resume_task_id/cleanup_tasks为逻辑关联，执行时另核对已有任务和恢复计划。新job.id成为tasks.id后，通过collection_plan_executions.task_id连接恢复计划。每次续采新建申请和执行，共用原plan_id；单模块补采为新计划，通过检查点resolved_by_task_id解除原失败项提示，不改旧错误。

collection_jobs.task_id为空时，没有执行日志、业务批次或恢复计划是合法状态。派发状态started只表示交给执行器，结束结论由tasks读取；不能据此判断仍运行。新执行不能绕过浏览器跨进程锁，数据库领取令牌不能替代该锁。
