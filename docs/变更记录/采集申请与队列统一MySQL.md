## 运行方式

申请先保存到collection_jobs。后台在资源行锁内领取，取得领取令牌，再启动独立进程。进程只接收工作空间、申请编号和领取令牌，连接定位通过进程环境传递，完整采集参数从MySQL读取。配置只保存密码环境变量名，不保存密码值。

申请等待时tasks可以不存在。统一执行器创建tasks与关联collection_jobs.task_id在一个事务内完成；执行状态、时间和结论只读tasks，不在作业表重复保存执行结论。业务快照和恢复检查点继续同事务确认。当前恢复、清理及模块跳过规则保持。

collection_queue_states按浏览器资料目录资源键保存暂停，空队列也保留。collection_job_controls保存目标任务、领取令牌、当前提示编号、动作与接收结果。正常停止及人工反馈读写数据库；数据库不可用时，只有已核实本地进程归属的紧急停止可以暂存，继续及确认不能绕过存储等待。

同一次提交编号永久关联原申请；在途相同范围合并。执行结束后释放参数去重键，主动再采可以创建新申请。启动失败和启动前取消留在申请表，不制造tasks。领取失效的进程不能启动或写入；创建入库前取消的流水确认作废，不补造执行、不阻塞下一次补写。

网页最近任务、队列、活动采集、商品任务和恢复入口均读MySQL。CLI关键词明细采集、选模块详情采集及续采登记同一作业表；仅搜索或仅打开页面没有采集申请。资源忙时CLI申请留在数据库队列，网页可以查看。正常新申请不能在断库时启动。

停止、关采集浏览器、全局异常暂停队列；Web重启保留仍活跃的采集，等待申请暂停，不自动开浏览器。先补写紧急停止及队列暂停，再补写事件；补写只保存数据。恢复某一任务是指定申请的单次领取，不放行其他暂停申请；继续队列才恢复自动派发。

## 表与数据迁移

0001～0008迁移及冻结模型不改写。0009创建collection_jobs、collection_queue_states、collection_job_controls，把旧collection_retry_queue记录逐项保留到统一作业表，核对无遗漏后移除旧队列表。结构为25张业务表、1张迁移版本表，共315字段。

旧等待请求迁入暂停状态；缺少完整配置时migration_pending=true，不能领取。单独的migrate-collection-jobs命令只读取当前正式派发目录，核对文件编号、数据库、资源键、配置和已有任务后迁移描述。已有任务建立外键关联，没有执行的旧申请不补造任务。缺少恢复计划的旧记录不标成可续采。不读取备份、不恢复退役的历史导入。

迁移核对源文件SHA256，重复运行不重复生成记录。旧文件保留为迁移来源，正常网页和执行器不再读取。图片、视频、HTML、原始JSON/CSV、浏览器资料、安全锁和可靠事件缓冲继续按原用途保留。

## 操作示例

在项目CMD中执行：

```cmd
.venv\Scripts\python.exe main.py database upgrade
.venv\Scripts\python.exe main.py database migrate-collection-jobs
.venv\Scripts\python.exe main.py database check
```

upgrade需要无活跃任务并取得两平台资源锁；migrate-collection-jobs仅迁移当前派发记录，不执行采集；check只核对结构。停止申请后网页显示正在停止，执行器确认后显示终态。申请入库后网页可显示等待执行，当前任务继续运行。
